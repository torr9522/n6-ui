# N5-UI Development Architecture

## 1. 项目定位

N5-UI 是基于 `n3-ui` 的二次开发项目。

项目目标：

- 在保持 `x-ui` 运行生态兼容的基础上增加增强功能
- 通过模块化扩展逐步引入出口线路池、落地管理、健康检测与调度能力
- 避免在早期开发中破坏已有脚本、服务、数据库和 API 兼容层

必须明确区分以下两个概念：

- 品牌层：`N5-UI`
- 运行兼容层：`x-ui`

品牌层用于：

- README
- 项目文档
- 页面标题
- 导航中的项目展示名
- 仓库说明

运行兼容层用于：

- 服务名
- 二进制名
- 安装命令
- 配置目录
- 数据库路径
- API 前缀
- Xray 调用逻辑

禁止混淆品牌层与运行兼容层。

## 2. 核心兼容冻结区域

以下文件或区域属于兼容冻结区域：

- `x-ui.sh`
- `x-ui_en.sh`
- `install.sh`
- `install_en.sh`
- `x-ui.service`
- `config/`
- `database/` 核心模型
- `xray/` 配置核心生成逻辑
- `/xui/` API 路径

冻结区域规则：

- 任何新功能不得直接修改上述区域
- 如确有必要修改，必须先提交兼容性评估文档
- 修改前必须说明是否影响已有 `x-ui` 安装用户
- 修改后必须提供回滚方案

默认原则：

- 能不动冻结区，就不动冻结区

## 3. 新功能开发原则

未来新增模块必须采用独立目录和独立分层。

后端必须独立为：

- 独立 model
- 独立 service
- 独立 controller

前端必须独立为：

- 独立页面
- 独立导航入口

示例：出口线路池

后端建议结构：

- `web/model/egress`
- `web/service/egress`
- `web/controller/egress`

前端建议结构：

- `pages/egress`

禁止以下做法：

- 直接把新功能塞进现有节点管理逻辑
- 直接把新功能混入原有 `x-ui` 兼容目录
- 为了快速上线而在旧 service 中堆叠大量条件分支

## 4. Xray 扩展原则

所有 Xray 增强功能必须通过 service 层生成扩展配置。

正确方式：

`egress service`  
`->` 生成新增 `outbound` / `routing fragment`  
`->` 与现有 Xray 配置做受控合并  
`->` 输出最终运行配置

错误方式：

- 直接修改原节点生成逻辑
- 直接改写原始入站配置生成流程
- 在核心 Xray 兼容逻辑中硬编码新业务规则

约束：

- 原 `xray` 核心目录应视为稳定兼容层
- 新功能只能生成“附加配置”，不能重写“原始配置来源”
- 配置合并必须由明确的 service 负责，不允许分散在多个 controller 中

## 5. 数据库扩展原则

新增功能必须优先新增数据表。

禁止：

- 随意修改已有表字段
- 在原有 `node`、`inbound` 等核心表中堆积大量新业务字段
- 没有迁移策略就直接改现有模型结构

推荐方式：

- 新建 `egress_nodes`
- 新建 `egress_policy`
- 新建 `egress_health_status`
- 新建 `egress_dispatch_logs`

而不是：

- 直接给 `node` 表增加大量出口字段

数据库变更要求：

- 每次新增表都要说明用途
- 每次变更都要说明是否影响旧安装
- 每次变更都要明确是否需要迁移

## 6. 前端规范

新增一级功能必须独立导航。

例如：

- 出口线路池
- 落地策略
- 健康检测

禁止：

- 把一级功能直接塞入“节点管理”
- 把复杂功能隐藏在“面板设置”中
- 让旧页面同时承担兼容功能和新业务功能

前端组织原则：

- 兼容层页面保持稳定
- 新业务页面独立维护
- 导航分组清晰，避免后续继续向旧页面堆功能

## 7. 后续开发路线

规划阶段如下：

- Phase 1：品牌迁移
- Phase 2：出口线路池基础
- Phase 3：落地策略
- Phase 4：健康检测
- Phase 5：线路池调度

每个阶段都应遵守：

- 优先新增模块，不侵入兼容层
- 先建边界，再做功能
- 先能关闭，再能默认启用

## 8. 开发提交规范

以后每次修改必须说明以下内容：

- 修改模块
- 影响范围
- 是否影响 `x-ui` 兼容
- 是否需要迁移

建议在提交说明、PR 描述或变更文档中至少包含：

- `Module:` 本次修改所属模块
- `Scope:` 影响到的目录和功能
- `Compatibility:` 是否影响 `x-ui` 兼容层
- `Migration:` 是否需要数据库或配置迁移

最低要求：

- 没有兼容说明的改动，不应合并
- 涉及冻结区的改动，必须先审计
- 涉及数据库的改动，必须先明确迁移方案

## 9. 架构红线

以下行为视为架构红线：

- 为了新功能直接改 `install.sh` 逻辑
- 为了新功能改 `x-ui.service` 名称
- 为了新功能改 `module x-ui`
- 为了新功能改 `/xui/` 现有 API 前缀
- 为了新功能把大量字段直接塞进核心旧表
- 为了新功能直接修改原 Xray 核心生成逻辑

如果未来确实必须突破红线，必须先单独形成兼容性变更提案，而不是在功能开发中顺手修改。
